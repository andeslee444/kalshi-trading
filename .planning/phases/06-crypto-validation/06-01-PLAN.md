  <action>
Create `scripts/crypto-backtest.py` with the following structure. Use the same path setup pattern as `scripts/backtest.py` (sys.path.insert for src/kalshi/).

**Subcommands via argparse:**
- `--fetch` — download and cache all three data sources
- `--settlement-audit` — time-to-settlement analysis (Task 2)
- `--backtest` — model replay (Plan 02)
- `--vol-sweep` — parameter optimization (Plan 02)
- `--force` — re-download even if cache exists

**Cache directory:** `PROJECT_DIR / "data" / "crypto-validation"` — create with `mkdir(parents=True, exist_ok=True)`.

**1. Coinbase candle fetching (`fetch_coinbase_candles`):**
- Use Coinbase Exchange API: `https://api.exchange.coinbase.com/products/{asset}-USD/candles`
- Parameters: `start` (ISO 8601), `end` (ISO 8601), `granularity=900` (15 min)
- Max 300 candles per request. 90 days = ~8,640 candles = ~29 requests per asset.
- Paginate by time windows: each batch covers `300 * 900 = 270,000` seconds (~3.125 days).
- Response format: `[[timestamp, low, high, open, close, volume], ...]` (NOTE: it is TLHOVC, not OHLCV).
- **Important:** Coinbase returns candles in DESCENDING order (newest first). Reverse after fetching so the cache is sorted ascending by timestamp.
- Use `retry_request("GET", url, timeout=15)` for HTTP calls.
- Sleep 0.5s between requests to avoid rate limits.
- Cache to `data/crypto-validation/coinbase-candles-{asset}.json`.
- Fetch for BTC, ETH, and SOL.

**2. Deribit DVOL fetching (`fetch_deribit_dvol`):**
- Endpoint: `https://deribit.com/api/v2/public/get_volatility_index_data`
- Parameters: `currency={asset}`, `start_timestamp={ms}`, `end_timestamp={ms}`, `resolution=3600` (hourly)
- Chunk into 7-day windows (~13 requests for 90 days).
- Response: `{"result": {"data": [[timestamp_ms, open, high, low, close], ...]}}`.
- Sleep 0.3s between requests.
- Cache to `data/crypto-validation/deribit-dvol-{asset}.json`.
- Fetch for BTC and ETH only (SOL has no DVOL — Pitfall 4 from research). Log a message for SOL explaining the limitation.

**3. Kalshi historical crypto markets fetching (`fetch_kalshi_crypto_markets`):**
- First call `GET /historical/cutoff` via `client.get("/historical/cutoff")` to determine the partition boundary.
- **Historical API:** Paginate `client.get("/historical/markets?status=settled&limit=1000")` using cursor. For each batch, filter to tickers starting with KXBTC, KXETH, KXSOL, or KXCRYPTO.
- **Live API fallback:** Also call `client.get_all_markets(prefix=prefix, status="settled")` for each CRYPTO_PREFIXES entry, merge by ticker dedup.
- Cache to `data/crypto-validation/kalshi-crypto-markets.json`.
- Print summary: total markets found, breakdown by asset prefix.

**Use `_atomic_write_json` for all cache writes.** Each fetch function checks for existing cache and skips unless `--force` is passed.

Print progress during fetching: asset name, batch count, total candles/points fetched.

<task type="auto">
  <name>Task 2: Implement time-to-settlement exhaustive audit</name>
  <files>scripts/crypto-backtest.py, src/kalshi/crypto-bot.py</files>
  <action>
Add the `--settlement-audit` subcommand to `scripts/crypto-backtest.py`.

**Settlement audit logic (`run_settlement_audit`):**

1. Load cached Kalshi crypto markets from `data/crypto-validation/kalshi-crypto-markets.json`. If not cached, error and tell user to run `--fetch` first.

2. For each market, compute actual duration:
   - Parse `open_time` and `close_time` fields (ISO 8601 with timezone).
   - Compute `actual_minutes = (close_ts - open_ts) / 60`.
   - Classify market type by duration bucket:
     - Hourly: actual_minutes < 120
     - Daily: 120 <= actual_minutes < 2000
     - Weekly: actual_minutes >= 2000
   - Also classify by asset using `parse_crypto_ticker(ticker)`.

3. Flag anomalies:
   - Markets where `close_time` is missing or unparseable.
   - Markets with actual_minutes <= 0.
   - Markets with result field empty or not in ("yes", "no", "all_yes", "all_no").
   - Markets that closed significantly earlier than expected (heuristic: hourly market closing in < 30 min).

4. Print settlement time distributions:
   - Per-type (hourly/daily/weekly): count, min, max, mean, median minutes.
   - Per-asset breakdown within each type.
   - List of anomalies with ticker and reason.

5. **Validate `estimate_time_to_settlement()`:**
   - Compare the typical durations found in the audit against the T=2456min assumption referenced in research.
   - If the existing `estimate_time_to_settlement()` logic in `crypto-bot.py` is correct (it uses `close_time - now` directly, which should be accurate for live markets), document that the function is correct.
   - If the logic has a bug or the T=2456min number is wrong, fix `estimate_time_to_settlement()` in `src/kalshi/crypto-bot.py`. The function currently reads `close_time` or `expected_expiration_time` from the market dict and computes minutes delta from now — this is the right approach for live trading. The audit's job is to verify that real market durations match expectations.
   - Print a clear verdict: "estimate_time_to_settlement() VALIDATED" or "estimate_time_to_settlement() FIXED: [description of fix]".

6. Save audit results to `data/crypto-validation/settlement-audit.json` containing:
   - `total_markets`, `by_type` (count + stats per bucket), `by_asset` (count per asset),
   - `anomalies` list, `verdict` string, `typical_durations` dict.
